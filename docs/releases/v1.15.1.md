# Puntovivo v1.15.1 — Colombian POS tickets keyed by CUDE

## Why this release matters

v1.15.1 corrects how Puntovivo identifies Colombian fiscal documents. The POS
documento equivalente and every credit or debit note are identified by DIAN
with a CUDE, computed with the software PIN, while only the electronic sales
invoice keeps the CUFE computed with the resolution technical key. Earlier
versions computed a CUFE for every document, and the shared hash layout still
carried a buyer field from the 2016 formula. Both official DIAN worked examples
now reproduce exactly.

The release also changes what happens when the DIAN configuration is
incomplete: a sale is no longer given a code DIAN cannot verify, its fiscal
obligation waits as blocked until the configuration is complete.

## What changed

### CUFE and CUDE

- The electronic sales invoice gets a CUFE. The POS documento equivalente,
  credit notes and debit notes get a CUDE.
- The hash follows the current DIAN annex: the issuer NIT and buyer ID are
  hashed without dots or check digit, the environment comes from the DIAN
  environment setting, and the date and time use the tenant's timezone with
  its offset instead of UTC.
- The draft XML uses type 20 for the POS ticket, 94 for credit notes and 93
  for debit notes, and declares whether its code is a CUFE or a CUDE.
- Receipts, ESC/POS printing, sale details, the fiscal document drawer, the
  CSV export and the default POS ticket template label the code CUFE or CUDE
  according to the document kind.

### DIAN configuration

- The Colombia DIAN card captures the DIAN software ID and software PIN. The
  PIN is write-only: once saved, the card only shows that it is configured.
- The PIN is never copied into queued fiscal payloads. It is read from the
  current settings at emission and redacted from the diagnostics export.
- Emission requires a valid issuer NIT, with its verification digit, and the
  software ID and PIN. Without them the obligation is blocked with a clear
  reason in fiscal operations, and setup readiness applies the same NIT rule.
- After completing the configuration, Recheck on a blocked obligation reads
  the issuer data again and emits the document with the correct code.

## Before you use it

- Colombian tenants with DIAN enabled must enter a valid NIT and the DIAN
  software ID and PIN before selling. Until then, new sales keep their fiscal
  obligation blocked instead of receiving a local code.
- Fiscal documents queued before this update for a Colombian tenant that had
  no DIAN configuration move to dead letter when they are emitted, and retry
  cannot recover them. They only held local mock codes, and changing their
  inputs would alter documents that already own a number.
- This update adds no database migration. Installed registers are offered it
  through the staged rollout; let a register finish its shift before
  restarting into it.
- Production sale is still gated by fiscal certification and physical-hardware
  validation, as the
  [project status](https://github.com/johnny4young/puntovivo/blob/main/docs/PROJECT-STATUS.md)
  describes.
