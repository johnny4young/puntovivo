# Puntovivo v1.17.0 — Electronic invoices on request and a desktop app that keeps up while it sells

## Why this release matters

In Colombia, the POS equivalent document has no amount limit. The 5 UVT rule
that used to push larger sales to an electronic invoice was written for the old
paper ticket. What the rules do require is that a buyer who asks for an
electronic invoice gets one. Until now a cashier had no way to honour that
request. v1.17.0 adds it to the payment drawer and to the touch POS, and asks
for buyer data only when the buyer wants the invoice in their name.

The desktop app also moves its built-in server off the thread that draws
windows and answers the screen. Menus, dialogs and every action on screen stay
responsive while sales are being processed.

## What changed

### An electronic invoice when the buyer asks for one

- Checkout shows **The customer asked for an electronic invoice** only at sites
  that can number one. It is off by default, and the buyer fields appear only
  once it is on.
- The cashier enters the name or business name, the ID type and number, and an
  optional email. A NIT is checked against its verification digit, and the
  screen shows how it will be recorded. An ID the invoice would reject, such as
  a number that is too short or the consumidor final number, is flagged before
  charging.
- The fields fill in from the attached customer and follow a change of
  customer. Corrections the cashier typed are kept. The request is cleared
  after each sale and when the ticket is cleared, so the next customer never
  inherits a buyer.
- Without a request, every sale issues the POS equivalent document, whatever
  its amount. A credit note on an invoiced sale refers to that invoice.
- The rule and its sources are in
  [the fiscal integration guide](https://github.com/johnny4young/puntovivo/blob/main/docs/FISCAL-INTEGRATION.md).

### A desktop app that stays responsive while it sells

- The built-in server now runs on its own thread inside the app. With the
  server busy selling non-stop on a test machine, the share of time the window
  thread was blocked went from about 22% to 0%. A screen action's round trip
  went from 27 ms to under 1 ms in the slowest 1%.
- Sales themselves are not faster. On four-core test runners under that same
  non-stop load, the server processed 20 to 30% fewer sales per second than
  before. On a faster eight-plus-core machine the rate did not change.
- A server that does not close cleanly now stops a backup restore or a key
  rotation, instead of letting it run over files that were still open.
- If the server thread fails, the app logs it, shows the error dialog and
  closes, as it did before.

### Fixes

- The scanner asks to rescan a code whose check digit fails, instead of
  searching for a product that does not exist.
- On the first Windows launch, the window now opens while the app saves its
  key.
- An open kitchen, payment or companion screen no longer blocks quitting, a
  backup or a restore.
- The demo products carry valid EAN-13 barcodes.

## Before you use it

- This release adds no database change.
- The electronic-invoice request appears only where the site has an active
  numbering range for invoices. There is no screen to register that range yet,
  so on a new installation the request stays hidden.
- Windows builds are not code-signed yet, so a downloaded update waits for
  **Restart to install update** in the tray menu instead of installing on quit.
- Production sale is still gated by fiscal certification and physical-hardware
  validation, as the
  [project status](https://github.com/johnny4young/puntovivo/blob/main/docs/PROJECT-STATUS.md)
  describes.
