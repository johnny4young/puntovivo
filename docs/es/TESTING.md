# Pruebas y validación de versiones

**Idioma:** Español · [English](../TESTING.md)

Este documento describe el contrato de validación vigente. Es una referencia operativa, no un registro de trabajo futuro. Los conteos y las mediciones de calificación que aparecen a continuación son evidencia histórica del candidato descrito, no una validación nueva del checkout actual.

## Concurrencia de fixtures del servidor

El ejecutor Vitest del servidor usa como máximo cuatro workers y nunca supera el valor predeterminado de Vitest de uno menos que el paralelismo disponible de la CPU. Cada worker migra repetidamente fixtures de SQLite y ejecuta hashing nativo de contraseñas; multiplicar ese trabajo por los núcleos del host puede agotar la memoria o el tiempo de comprobaciones de ciclo de vida que, por lo demás, están acotadas. Esto controla únicamente la concurrencia de los fixtures: no se flexibiliza ninguna suite, aserción, umbral de cobertura ni tiempo límite. Los perfiles estrictos de rendimiento siguen ejecutándose por separado, sin superponerse con otras validaciones de los workspaces. Las comprobaciones del ciclo de vida del llavero separan el reinicio, el reemplazo y cada contrato de entrada no válida, en lugar de incluir cinco arranques del servidor en el presupuesto de una sola prueba.

## Validaciones obligatorias por workspace

Ejecuta los comandos desde la raíz del repositorio.

| Área modificada                                                              | Comando obligatorio                             |
| ---------------------------------------------------------------------------- | ----------------------------------------------- |
| Contratos compartidos                                                        | `pnpm run ci:shared`                            |
| React o aplicación del navegador                                             | `pnpm run ci:web`                               |
| Fastify, tRPC, base de datos o servicios del servidor                        | `pnpm run ci:server`                            |
| Proceso principal de Electron o puente preload                               | `pnpm run ci:desktop`                           |
| Contrato crítico acotado del navegador                                       | `pnpm run test:e2e:web:critical`                |
| Inicio de sesión, ventas, inventario, importación o E2E del navegador        | `pnpm run test:e2e:web`                         |
| Ciclo de vida del renderer durante turnos largos o UI sensible a fugas       | `pnpm run test:e2e:web:soak`                    |
| E2E de arranque, IPC, respaldo o actualizador de Electron                    | `pnpm run test:e2e:electron`                    |
| Automatización de versiones                                                  | `pnpm run ci:release`                           |
| Ensayo de actualización, rechazo de versión anterior y restauración cifrados | `pnpm run rehearse:upgrade-recovery`            |
| Un ensayo de recuperación del escritorio empaquetado                         | `pnpm run rehearse:packaged-recovery -- <args>` |

Los comandos de CI de los workspaces incluyen comprobación de tipos, lint, pruebas, auditoría de dependencias y las mediciones de compilación o ejecución que correspondan a ese workspace.

`ci:release` incluye los contratos del veredicto de confianza de distribución y del resolvedor del binario empaquetado mediante `test:release-script`. La automatización de versiones de las pull requests se ejecuta cuando cambia cualquiera de esas pruebas o su implementación, mediante el filtro existente de rutas `scripts/**`. Ambos contratos usan resultados inyectados de herramientas de confianza y fixtures temporales de la distribución de ejecutables; no firman, notarizan, ejecutan ni certifican un distribuible real. La confianza real del sistema operativo y la ejecución empaquetada siguen requiriendo las comprobaciones del candidato a versión que se indican más adelante.

Una prueba de registro en `scripts/ci-path-filters.test.mjs` falla cuando un archivo `scripts/*.test.mjs` o `scripts/*.test.mts` no se ejecuta desde una validación alcanzable por algún job de CI, para que una prueba nueva de scripts no omita CI silenciosamente.

### Aislamiento de la suite web del navegador

Los comandos web de Playwright compilan el servidor antes de la configuración global. Esa configuración inicializa `packages/server/data/local.db`, sin cifrar y propiedad de la suite, mediante las migraciones y la semilla predeterminada del servidor; luego prepara las identidades E2E. Esto funciona en un checkout nuevo sin depender del tiempo de arranque del servidor ni de la base compartida de un desarrollador. Playwright inicia su propio servidor independiente `device_local` en loopback, en el puerto 8090, y el renderer Vite en `http://localhost:5173` de manera predeterminada; el modo Hub heredado o los ajustes de enlace LAN no pueden modificar ese servidor. Ambos procesos hijos propios usan explícitamente el modo de desarrollo para este fixture en texto plano, aunque el shell del operador indique producción; el arranque independiente en producción sigue requiriendo SQLCipher. Playwright no reutiliza un listener existente ni ejecuta el lanzador de desarrollo, que podría detener la aplicación de otro worktree en el puerto 3000. Una colisión de puertos hace fallar la ejecución en vez de tomar prestado otro proceso. Conserva el contrato configurado de cuatro workers y cero reintentos de la suite completa; el subconjunto crítico acotado sigue siendo serial en CI.
La suite también falla antes de abrir el navegador si el `.env` local seleccionado por el servidor define `PUNTOVIVO_DB_KEY`: el fixture en texto plano no debe tomar silenciosamente la configuración SQLCipher de un operador. Ejecuta esa validación en un worktree limpio en lugar de debilitar la política de cifrado independiente.
`PUNTOVIVO_E2E_API_ORIGIN` permite seleccionar otro puerto de backend propio. Debe ser un origen HTTP en `localhost` o `127.0.0.1`, con un puerto explícito no predeterminado distinto del puerto web dedicado 5173, y sin credenciales, ruta, consulta ni fragmento. El renderer, la sonda de salud, el enlace del backend y las sondas directas HTTP/CLI usan ese mismo puerto. El origen web propio usa el nombre de host de la API en el puerto 5173 para que las cookies estrictas de renovación sobrevivan a la navegación completa; no se flexibiliza la política de cookies de producción. Los valores de reemplazo no válidos fallan antes de iniciar cualquier servicio de prueba.

### Control incremental de tipos de pruebas del servidor

`ci:server` ejecuta la comprobación de tipos del servidor de producción y luego una comprobación independiente de tipos de pruebas mediante `packages/server/tsconfig.tests.json`. La configuración de pruebas conserva toda la rigurosidad de producción, amplía `rootDir` solo lo necesario para incluir los fixtures importados por el servidor y expone la biblioteca ES2024 implementada por el runtime obligatorio Node 24. No amplía la configuración de compilación de producción.

La suite actual tiene una línea base versionada de 227 diagnósticos en 111 archivos. `test-typecheck-baseline.json` registra los conteos por archivo y código de diagnóstico, no por número de línea. Los metadatos no válidos, contadores no enteros y totales incoherentes se rechazan antes de la comparación, al igual que los diagnósticos sin ubicación o de `tsconfig` y la salida del compilador no reconocida, porque pueden detener u ocultar toda la comprobación. Un par nuevo de archivo/código o un conteo mayor falla; un diagnóstico resuelto también falla hasta que se reduzca deliberadamente la línea base. Esto evita deuda nueva y garantiza que las mejoras no dejen una tolerancia obsoleta. Después de revisar la salida sin procesar del compilador, los mantenedores pueden regenerar la instantánea reducida con `pnpm --filter @puntovivo/server run typecheck:tests:update`; CI nunca la actualiza automáticamente. Superar este control significa que no se agregó deuda de tipos respecto de la instantánea, no que todas las pruebas del servidor estén libres de errores de tipos.

### Umbrales de cobertura del servidor

`pnpm --filter @puntovivo/server run test:coverage`, que ejecuta `ci:server`, exige los umbrales V8 declarados en `packages/server/vitest.config.ts`: mínimos de sentencias, ramas, funciones y líneas de **85%, 76%, 82% y 87%**, respectivamente. Los umbrales conservan aproximadamente entre 1.6 y 2.4 puntos porcentuales de margen respecto de mediciones repetidas del backend con el mismo alcance (aproximadamente 87%, 78.4%, 84% y 88.6%), suficientes para absorber variaciones entre ejecuciones y detectar una regresión real. Súbelos cuando aumente la línea base medida; no los reduzcas sin una justificación documentada.

El alcance medido incluye cada archivo fuente del servidor que carga la suite, excepto archivos de prueba, migraciones generadas, `src/standalone.ts`, el directorio `scripts/` a nivel del paquete y archivos de configuración. La configuración no define `coverage.include`, por lo que un módulo que ninguna prueba importa queda fuera del denominador en lugar de contarse como no cubierto: los umbrales detectan regresiones en el código ejercitado, no en un archivo nuevo sin pruebas. Las CLI de desarrollo probadas dentro de `src/scripts/` forman parte del agregado. Un agregado aprobado no demuestra que estén cubiertas todas las rutas de tenant, fiscales o de rollback; las pruebas enfocadas en invariantes siguen siendo obligatorias para esos cambios.

## Shell adaptable del operador

`e2e/web/header-responsive.spec.ts` ejercita tenants reales y aislados con nombres largos de empresa, sede y empleado en inglés y español. Comprueba los controles del encabezado a 320, 390, 640, 768, 1024, 1280, 1440, 1536 y 1920 píxeles CSS, incluido el cierre del menú de cuenta con Escape y la restauración del foco, la selección de sede y su persistencia tras recargar, el desbordamiento horizontal y la accesibilidad con axe. La selección de idioma y sede sigue disponible en pantallas estrechas; la búsqueda compacta conserva su nombre accesible y atajo de teclado. Las regresiones de componentes también cubren el cierre al pulsar fuera sin quitarle el foco al control seleccionado.

## Regresiones de lease y persistencia del outbox

Las pruebas del núcleo y del worker rechazan tenants/tokens incorrectos, éxito/fallo tardío y reactivación de estados terminales. Las pruebas concretas de alertas operativas recuperan un lease vencido mientras HTTP está en curso y conservan al ganador junto con el historial del intento interrumpido. Un fallo de metadatos inducido por un trigger demuestra que la evidencia del intento final y la confirmación se revierten juntas.

`fiscal-worker-lease.test.ts` usa el worker real y SQLite para demostrar que los resultados tardíos aceptados/recuperables/permanentes no pueden modificar el documento, CUFE, evento aceptado ni metadatos; un fallo local de SQL no puede convertirse en un rechazo fiscal; y los errores opcionales de eventos/metadatos no provocan un segundo envío al proveedor. Las pruebas de webhooks cubren pérdida del lease durante DNS, respuestas HTTP tardías y conservación del éxito por suscriptor entre reintentos. Los efectos sobre proveedores externos e impresoras siguen siendo de entrega al menos una vez, no una entrega exactamente una vez certificada.

## Contratos de perfiles verticales y medida variable

Ferretería y carnicería reutilizan el núcleo transaccional minorista, pero agregan evidencia de configuración explícita y acotada:

- las pruebas compartidas fijan los seis ID de perfil, las cinco plantillas de producto solo para formularios, el fallo de resolución de unidades sin modificar el catálogo, el mapeo GS1 histórico, los prefijos configurables/ignorados y el mínimo operativo de UI de `0.001`;
- las pruebas del router de presets de módulos aplican ferretería y luego carnicería con sobres de comando nuevos y comparan cada categoría, producto y unidad del tenant antes y después, conservando los ajustes de IA e integraciones fuera del parche;
- las pruebas de escáner/parser/router cubren filas predeterminadas, mapas tipados de prefijos, rechazo de solapamientos/valores vacíos/fuera de rango, `gs1Scheme: none`, filas heredadas corruptas, política de checksum y significados distintos del mismo código en dos sedes sin filtraciones entre tenants; los kilogramos de balanza requieren una unidad base de masa explícita, se convierten mediante su factor de referencia en gramos y se vuelven a comprobar contra la política de enteros/fracciones/mínimo/paso del producto antes de entrar al carrito. Los códigos de medida variable no pueden resolver un código de barras de empaque, y las etiquetas de solo precio se rechazan de forma segura para productos fraccionarios que requieren un payload de peso. Si falta una sede activa se deshabilita la decodificación embebida en vez de aplicar una suposición global del tenant;
- las regresiones de venta, compra, pedido, política de fracciones, unidades alternativas y carrito conservan un milésimo exacto en lugar de redondearlo a una cantidad centesimal; varias etiquetas de peso se acumulan, los empaques enteros con precios distintos conservan claves independientes exactas en el carrito y las líneas duplicadas de producto/unidad sobreviven a un recorrido real crear→suspender→retomar en el servidor. El dinero sigue redondeándose mediante el contrato independiente de dos decimales;
- las pruebas del modal de producto y del formulario de periféricos exigen un clic explícito en la plantilla, resolución de unidad física activa, conversión de masa positiva, fallback de Tier 2/Tier 3, coherencia inmediata del perfil confirmado, controles tipados de roles 20–29 y prevención de un mapa de prefijos vacío. Las regresiones del omnibox también demuestran que se aplica el nivel existente del cliente cuando Ventas no está montado, mientras los precios reemplazados por GS1 siguen congelados. La integración de cobro rechaza un precio fuera de catálogo de un cajero sin `sale_price_override`, rechaza una autorización después de que cambie el precio exacto, la consume una vez, emite la auditoría inmutable del cambio y repite el mismo límite para un borrador congelado mostrado después de retomarlo. La comprobación previa propiedad del servidor cubre precios exactos de catálogo, cambios remotos del catálogo, borradores congelados y una sonda de producto de otro tenant; una regresión de componente demuestra que su acción sigue visible aunque los metadatos locales del catálogo indiquen que la línea no cambió. Un smoke en navegador real y aislado agrega primero la línea, modifica después el catálogo persistido y observa la acción de autorización exigida por el servidor en el panel de cobro abierto del cajero, sin errores del cliente;

La calificación con el destino en ejecución y aislado del 2026-09-01 aplicó ambos perfiles desde la UI autenticada, confirmó plantillas específicas por perfil, creó y recargó productos MT y KG con `0.001`, persistió el mapa de escáner de la sede activa y envió una ráfaga real de teclado emulado cuyo lookup en el servidor agregó `0.199 kg` al carrito. La secuencia administrativa larga alcanzó el límite de solicitudes de desarrollo antes de su consulta final, por lo que el escaneo final se repitió tras el período de espera como continuación acotada, con cero errores del cliente del navegador. Se conservaron capturas con la evidencia local de la tarea. La certificación física de escáner/balanza, conformidad de etiquetas por país, metrología legal y certificación de línea de producción siguen fuera de ese smoke de perfiles. El smoke de perfiles es anterior al motor transaccional independiente de transformaciones; su evidencia de software enfocada se describe más adelante y no convierte una plantilla de catálogo en una ejecución.

## Contratos del servicio de restaurante

La calificación de restaurante trata el flujo de mesas como una máquina de estados respaldada por ventas:

- las pruebas de integración del servidor abren cuentas con callers reales de tRPC y sobres de comando, y luego inspeccionan las filas persistidas de venta, existencias, auditoría, servicio, cuenta, comensal, tiempo de comida, ronda, línea, modificador y compatibilidad KDS. Repetir un sobre fijo debe devolver la misma venta y crear una sola vez cada nodo del grafo;
- la capacidad, cantidad establecida de invitados, cantidad de comensales activos, sede de la mesa, estado del módulo, límites de solicitud de 100 cuentas/200 líneas/20 modificadores y límites de proyección del servicio de 1,000 líneas/4,000 modificadores fallan antes de confirmar un grafo parcial. Una apertura rechazada demuestra rollback de venta, consecutivo y existencias. Las pruebas de catálogo de mesas ejercitan paginación estable y rechazan atómicamente una mesa activa que supere el límite por sede, incluida la reactivación de filas archivadas;
- varias cuentas siguen visibles en una misma mesa. Completar y descartar cierran solo su cuenta, y el servicio se cierra tras la última cuenta abierta. Las pruebas de división en una mesa conservan nivel de precio, tiempo de comida, ronda, modificadores, identidad compatible del comensal, existencias y alcance de tenant/sede; concilian proporcionalmente descuentos de cabecera, propinas, cargos de servicio, totales y pagos provisionales, y rechazan borradores indivisibles de fidelización/crédito de tienda. Las pruebas de cambio de mesa conservan el servicio y sus comensales para una cuenta única y rechazan servicios de origen con cuentas compartidas, destinos ocupados y asignación implícita del grupo entre mesas;
- una regresión de reanudación competitiva ejecuta dos intenciones de comando distintas contra una venta suspendida y permite exactamente una transición y una fila de auditoría. Un recorrido independiente con dos cajeros lista, retoma, vuelve a aparcar y liquida una cuenta normalizada en la misma sede, manteniendo privados los borradores minoristas no relacionados; las aserciones de recibo y auditoría distinguen a quien abrió la cuenta del cajero que la liquida. Las regresiones de archivo/actualización de mesas ejecutan sus guardas de servicio abierto bajo el mismo bloqueo inmediato de escritura. Las pruebas de alternancia de módulo y presets demuestran que `dine-in` no se puede deshabilitar mientras quede trabajo de mesa normalizado o heredado;
- las pruebas de migración actualizan desde la entrada anterior del journal, adoptan borradores de mesas activas incluidas filas ya retomadas, dejan intactos los borradores de mesas archivadas y el historial completado, fijan de forma segura el delta de modificador de compatibilidad, verifican claves foráneas, conservan la cancelación de borradores históricos sin sesión de caja y demuestran idempotencia al reiniciar;
- las pruebas de componentes de pedidos por voz ejercitan entrada manual y por voz, modificadores estructurados, notas, selección de comensal/tiempo, supresión de doble clic, recuperación de fallos de comando, todas las cuentas abiertas, bloqueo del conteo de invitados, bloqueo completo del editor mientras el comando atómico de apertura está pendiente, capacidad, controles de módulo/sesión, estados seguros de carga/error/vacío, metadatos de accesibilidad EN/ES, paridad táctil/móvil y todas las proyecciones de inventario, producto, movimiento y serie invalidadas tras confirmar una reserva. Las pruebas del POS tradicional cubren aparcado genérico y selección explícita de mesa sin usar silenciosamente la capacidad como tamaño del grupo. ## Contratos de comandos de compras y sede de movimientos

El límite de compras tiene regresiones enfocadas más allá del CRUD habitual del router:

- repetir sobres fijos de creación de compras y pedidos devuelve el resultado canónico persistido y crea exactamente un efecto de agregado/auditoría/cabecera de outbox; los efectos de outbox de líneas de pedido aparecen una vez por línea persistida, sin duplicarse por repetición;
- un fallo forzado en la escritura de éxito de idempotencia revierte juntas las filas de compra, numeración, existencias, movimientos, auditoría y outbox;
- una segunda conexión SQLite mantiene `BEGIN IMMEDIATE` para demostrar que `COMMAND_DATABASE_BUSY` es seguro para presentar, no deja reserva ni escritura de dominio parciales y permite que el mismo sobre exacto tenga éxito una vez después de liberar el bloqueo;
- una fila abandonada en procesamiento conserva su propietario antes del límite del lease de 60 segundos, se puede recuperar en ese límite, rechaza que su propietario obsoleto la complete y no puede borrar al propietario que confirmó después de la instantánea del lector de toma de control;
- las regresiones del renderer demuestran que clics concurrentes, reintentos automáticos y reintentos posteriores del usuario tras resultados inciertos de transporte/ocupación reutilizan un sobre, mientras un rechazo terminal explícito del servidor cierra esa identidad;
- la migración `0050` actualiza una base `0049`, completa solo movimientos cuya sede de venta/sesión de caja, compra, devolución de compra o inventario inicial es autoritativa, conserva nulo el historial ambiguo y aprueba comprobaciones de claves foráneas e índices; y
- las consultas de inventario demuestran filtrado de sede seguro por tenant y la regresión web demuestra que los operadores pueden pasar de la vista de sede activa a todas las sedes más la evidencia histórica sin atribución.

## Contratos de conteo físico exacto

Las regresiones de integración de conteo por identidad cubren ocultamiento ciego de series, asignación exacta de lotes, diferencias opuestas con cantidad neta cero, rechazo de identidades desconocidas/ajenas, exclusión de series reservadas, ABA de custodia frente a ACK real de sincronización, procedencia de series faltantes/redescubiertas, conservación de lotes bloqueados y rollback cuando falla el outbox transaccional. Un lote activo contado a cero pasa a agotado; redescubrirlo requiere cuarentena en vez de devolverlo silenciosamente a la venta. El fixture de actualización aplica el journal anterior tanto a archivos cifrados como de texto plano y verifica adopción aditiva, reclasificación del outbox histórico pendiente, revisiones independientes de custodia y persistencia tras reabrir.

`e2e/shared/inventory-identity-count-journey.ts` ejecuta la UI real en web y Electron: recibe y pone en cuarentena lotes de farmacia, guarda conteos exactos entre recargas, revisa y aprueba diferencias opuestas entre lotes, recibe existencias serializadas, registra una unidad faltante, la redescubre y recarga el lado de lectura EN/ES. Las respuestas reales de conteo no deben contener códigos de serie no escaneados. El wrapper web además lee SQLite para conciliar custodia final de lotes, estado de series y garantía original. Las identidades iniciales de acceso se aprovisionan con fixtures; esto no demuestra onboarding de primer uso, instalación firmada, escáner físico ni certificación regulatoria.

## Contratos de compras de lotes exactos y transformaciones

La matriz de compras por lote ejercita compra directa, recepción de pedido, devolución a proveedor, anulación de compra, transferencia inmediata, transferencia diferida, recepción con diferencias y anulación de transferencia con lotes concretos en lugar de atajos de saldo agregado. Demuestra requisitos de asignación completa, topes por procedencia de compra, aislamiento de tenant/sede, conservación de vencimiento y cuarentena, costo ponderado congelado, rollback de devolución a proveedor y anulación de compra ante variaciones de costo, reversión exacta de capa de destino, repetición, rollback y coherencia de movimiento/auditoría/sincronización. Las pruebas de reposición también demuestran que una falta de producto con seguimiento por lote puede crear un borrador solo de cantidades, mientras su recepción posterior sigue bloqueándose de forma segura sin identidad física. Las observaciones escalares siguen rechazadas para líneas de conteo con seguimiento de identidad.
Las regresiones de custodia diferida despachan todo el saldo ordinario y demuestran que el seguimiento de existencias, lotes y series no puede cambiar solo porque ambas sedes ahora indican cero. Los metadatos de servicio corrompidos directamente provocan rechazo seguro en creación, recepción y anulación de transferencias sin cambiar saldos ni estado del ciclo de vida; restaurar el modo de inventario ordinario permite completar la misma operación exactamente una vez. Las regresiones de lectura de compras además agotan existencias ordinarias, trasladan un lote comprado, cambian una serie de origen a un producto ajeno y devuelven otra serie para demostrar que `remainingQuantity` puede seguir positiva mientras `returnableQuantity` sigue la evidencia física actual. Las opciones de lote exacto se fijan por separado en cero tras cambios de seguimiento, transferencia, anulación, cambio de identidad o recepción con costo combinado, para que un control de asignación hijo no contradiga su procedencia congelada ni el presupuesto seguro de la línea.

La matriz de transformaciones cubre ciclo de recetas globales y de sede, conflictos optimistas, elegibilidad de productos solo de existencias, coincidencia exacta de líneas de receta, insumos ordinarios y multilote, lotes nuevos de salida, roles principal/subproducto/remanente, desperdicio multilote, asignación del último centavo de costo, cantidades fraccionarias, existencias insuficientes y no vendibles, aislamiento de tenants, repetición concurrente, rollback transaccional y anulación protegida antes y después de consumir salidas o cambiar costos. Una regresión de costos divergentes demuestra que los insumos ordinarios se valoran desde `initialCost`, cada salida actualiza `cost` e `initialCost` independientemente, el KPI/listado de inventario usa la base resultante y una anulación sin cambios posteriores restaura ambos exactamente. Las regresiones web crean y editan recetas más allá de la primera página del catálogo, conservan alcance global, ejecutan lotes exactos, muestran detalle congelado, presentan errores de lectura sin estados vacíos contradictorios, ocultan diagnósticos internos del transporte de detalle de compra y construyen payloads de compra/transferencia conscientes de lotes. Las regresiones de detalle de compra y modal de devolución rotulan explícitamente la cantidad física y deshabilitan un lote agotado en lugar de ofrecer como existencias la cantidad recibida no devuelta. La regresión del modal de detalle también fija una ventana de frescura cero para que cerrar, modificar inventario y reabrir no reutilice una instantánea de retornabilidad de cinco minutos; los controles de débito en caché siguen bloqueados de forma segura durante la renovación.

El recorrido real del navegador crea dos productos con lotes, recibe un lote concreto del proveedor y abre primero la compra cuando sus cuatro unidades son retornables. Mantiene esa consulta en caché en la misma SPA, ejecuta una receta de 4 a 3, comprueba directamente en SQLite las filas y saldos congelados, exige el costo dual persistido de la salida y una contribución de valoración de COP 10,000 y concilia el KPI visible de todo el tenant con la base. Antes de que venza la ventana global de caché de cinco minutos, cambia al español mediante el control de idioma en vivo y reabre la misma compra por número. Exige una lectura nueva con cero unidades retornables, cantidad recibida y vencimiento conservados, estado actual del lote y ninguna acción de devolución a proveedor. Luego recarga la UI y reabre la evidencia de transformación. El recorrido de Electron repite la ruta del operador mediante el servidor integrado, cierra y vuelve a iniciar sesión y demuestra que la instantánea de lote/costo y la valoración visible siguen disponibles en la base cifrada de escritorio. Ambos recorridos fallan ante errores de consola, página, transporte o proceso de Electron.

La evidencia enfocada canónica es `packages/server/src/__tests__/lot-procurement-transfers.test.ts`, `packages/server/src/__tests__/inventory-transformations.test.ts`, las suites existentes de compra/pedido/conteo y las pruebas de componentes correspondientes de compra, pedido, transferencia, editor de lotes y transformación, además de `e2e/web/inventory-transformations.spec.ts` y `e2e/electron/inventory-transformation.spec.ts`. La migración `0056` está cubierta por validaciones de base nueva, actualización histórica, claves foráneas, índices, paridad del journal y adopción heredada. La forma deliberadamente limitada de adopción solo de compras fija `0056` únicamente cuando no existe ningún destino de lote, devolución, transferencia o transformación; una base mixta o parcialmente materializada mantiene pendiente la migración y falla de forma segura en vez de declarar completo un esquema incompleto.
[ADR-0018](architecture/0018-lot-procurement-and-transformations.md) define el límite durable y sus limitaciones externas reales.

## Contratos de conversión de cotizaciones y cuentas por pagar a proveedores

Las pruebas de conversión de cotizaciones ejercitan la transacción real de venta. Las regresiones del servidor fijan estado aceptado y no vencido, comparación de instantes ISO, paridad de tenant/sede/cliente/nivel/moneda y líneas exactas, migración de instantáneas de unidad, rollback ante cambios y un ganador bajo conversión concurrente. El recorrido del navegador acepta una cotización, abre su POS con términos bloqueados, la cobra una vez, demuestra un único débito de inventario, recarga y lee la venta vinculada autoritativa.

Las pruebas de cuentas por pagar fijan saldos iniciales explícitos, vínculos a compras completadas, dinero de dos decimales, fechas y orden del calendario del tenant, asignaciones completas, la ecuación `invoices - payments - credits = outstanding`, antigüedad, orden del estado de cuenta, conciliación de caja para pagos en efectivo, drenaje de sincronización admitida, repetición y rollback de sobres de comando, guardas de rol y aislamiento de tenants. El recorrido real del gerente registra una factura y monto inicial, asigna un crédito y pago empezando por lo más antiguo, llega a cero, recarga la cuenta y concilia los totales SQLite. Nunca recibe controles CRUD de proveedores.
El recorrido bilingüe del selector de compras siembra independientemente 101 compras sin facturar, encuentra la más antigua por paginación y búsqueda literal, conserva la selección y monto, registra su factura, recarga y concilia su vínculo exacto a compra/sede en SQLite. La respuesta sigue acotada a 25 filas.

Las regresiones monetarias mantenidas incluyen tres devoluciones sucesivas de un centavo contra tres pagos divididos (incluida repetición), particiones aleatorias de asignación de centavos enteros y aserciones de margen fechadas tras comandos reales de cobro/devolución. Los casos bilingües del libro de clientes rechazan ajustes que redondean a cero sin persistir una fila, muestran errores traducidos, se recuperan con un monto válido y recargan la entrada aceptada del libro. Las respuestas de validación esperadas se comprueban específicamente; los rechazos no manejados son fallos.

`scripts/e2e-baseline-cleanup.test.mjs` protege la repetibilidad de esos recorridos: los hijos restrictivos de AP y cotización-venta, más sus filas de sincronización AP, se eliminan antes de los padres E2E desechables, mientras usuarios de plantilla, datos del operador y otros tenants quedan intactos. Cada tenant E2E aislado comienza también sin sincronización en cola ni conflictos sin resolver: de otro modo una fila antigua de outbox cuya entidad desechable se eliminó se enviaría automáticamente y produciría un conflicto falso en el siguiente recorrido. Las reglas de promoción, instantáneas restrictivas de líneas de venta, filas de auditoría y vínculos lógicos de sugerencias de vencimiento se eliminan antes de su producto, cliente o actor desechable. El reinicio está acotado por tenant, es idempotente y tiene cobertura contra eliminación entre tenants. Esta limpieza de fixtures no es una ruta de eliminación de producción.

## Límites actuales de extremo a extremo

La suite del navegador cubre la ruta monetaria crítica del comercio minorista y los recorridos administrativos, incluidos autenticación, controles por rol, ventas, devoluciones normalizadas, anulaciones, compras, transferencias de inventario, sesiones de caja, importaciones, aprobaciones, prevención de pérdidas, asistencia del personal, variantes, series y firma del cierre diario.

La matriz del servidor de devoluciones normalizadas demuestra por separado cantidades parciales sucesivas, conciliación del último centavo de impuestos y pagos, recuperación exacta de lotes/series, reducción de saldo a crédito, emisión de crédito de tienda, vínculo de cambios, protección concurrente de la última unidad, repetición idempotente, aislamiento de tenant/sede y compatibilidad de migración. Los recorridos de reembolso de navegador y Electron seleccionan las líneas restantes desde el compositor real de devoluciones y verifican existencias restauradas y evidencia inmutable de auditoría de actor/motivo tras volver a autenticarse. Una regresión real independiente del navegador crea una venta con tarjeta, convierte sus filas de pago a la forma heredada admitida, registra la referencia requerida del proveedor desde el compositor, verifica en SQLite la asignación externa normalizada y recarga el ticket reembolsado. Esas pruebas no implican ejecución del reembolso de tarjeta del lado del proveedor.

La matriz de promociones y valor de clientes ejercita reglas versionadas en borrador, activas, pausadas y archivadas; aislamiento de tenant/rol; segmentación por producto, categoría, sede, cliente, cantidad y ventana UTC; precedencia exclusiva y combinable; prioridad del precio manual; huellas obsoletas; clientes heredados; conversión FEFO por vencimiento aprobada por gerente; y comportamiento seguro de rechazo en farmacia. Recorridos independientes del servidor fijan precios de puntos enteros, rechazo por saldo insuficiente y competencia por último saldo, pagos mixtos de fidelización/crédito de tienda, finalización de borradores, devoluciones sucesivas, restauración única al anular y paridad de libro/saldo materializado. El recorrido real del navegador configura la función, activa una promoción dirigida, cobra puntos + crédito de tienda + tarjeta, comprueba evidencia congelada de SQLite, recarga historial EN/ES, devuelve el ticket con evidencia externa del proveedor y concilia ambos libros de valor del cliente hasta sus saldos iniciales.

La matriz de integración de farmacia ejercita políticas de Colombia y países no admitidos, clasificación OTC/con receta/controlado, autorización efectiva del empleado, autenticación de evidencia cifrada, referencias duplicadas y vencidas, consumo parcial determinista, selección acotada de evidencia fragmentada alineada con el contrato de venta de 200 ID, rechazo de reutilización concurrente, aislamiento de tenant/sede, FEFO por lote, vencimiento, cuarentena, incidentes de cadena de frío, retiros sobre procedencia de compra y transferencia, devoluciones exactas, destrucción, devolución a proveedor, cambios de fecha comercial, adopción de migraciones y búsqueda de 50,000 productos. La cobertura de componentes fija motivos de bloqueo del perfil, cambios de sujeto en el cobro, renovación de aprobación de evidencia externa y límites de PII para gerente/administrador.

El recorrido compartido de día de farmacia en `e2e/shared/pharmacy-*-journey.ts`, ejecutado por `e2e/web/pharmacy-operations.spec.ts` y su equivalente Electron, crea datos operativos desde la UI: selección explícita de Colombia y recarga, perfil de farmacia, unidad, proveedor, medicamentos, compras de lotes exactos, apertura de caja, autorización profesional, cliente, registro y aprobación de receta. Comprueba búsqueda por ingrediente, FEFO OTC, cuarentena por cadena de frío, cobro bloqueado sin identidad/evidencia, orden no válido de fechas de receta, dispensación aprobada una sola vez después de recargar y medicamentos controlados que siguen deshabilitados pese a las existencias y credenciales profesionales. Luego el operador inicia un retiro de producto, lee el recibo afectado desde la tabla de retiros y reembolsa la unidad vendida exacta. El lote retirado recibe esa unidad sin volverse vendible, incluso tras recargar en español. El oráculo web concilia saldos SQLite por tenant/sede, asignación de dispensación, evidencia consumida y almacenamiento sellado de credenciales; los mismos pasos de UI se ejecutan contra el servidor integrado y la base cifrada de Electron.
El día también recibe un lote realmente vencido y exige un rechazo tipado del comando real de venta, registra una receta vencida y rechaza su aprobación, y luego cambia a un país no admitido desde ajustes de empresa. La dispensación OTC consume un lote válido recibido por separado; los medicamentos con receta y controlados siguen bloqueados. Los comandos fallidos no modifican caja, cantidades de lotes ni evidencia consumida. Las respuestas HTTP negativas intencionales se aceptan solo tras verificar procedimiento exacto, estado y error comercial; un contrato de diagnóstico independiente rechaza errores ajenos o duplicados.

El recorrido complementario `pharmacy-transfers.spec.ts` crea una sede de destino, envía cantidades exactas activas y en cuarentena, las recibe después de cambiar de sede y verifica su estado tras recargar. Localiza el recibo original mediante su proveedor, devuelve una unidad exacta en cuarentena del origen y concilia ambas sedes, asignaciones congeladas de transferencia y cantidad/costo de devolución a proveedor en SQLite.
El recorrido independiente `pharmacy-roles.spec.ts` crea cuentas de gerente y cajero desde la UI y cambia de actor mediante cierre autoritativo de sesión. Comprueba en la respuesta real del gerente la identidad de cliente redactada, controles profesionales de solo lectura, textos de privacidad EN/ES y redirección de ruta de cajero sin lecturas privadas de farmacia. Los wrappers web y Electron conservan capturas y rechazan diagnósticos inesperados del cliente; el destino de escritorio usa el servidor integrado y la base cifrada.

El aprovisionamiento inicial de identidad/empresa/sede sigue siendo requisito previo de pruebas, no evidencia de creación inicial del tenant desde la UI. Las carreras de dispensación concurrente y retiro tienen cobertura de integración, no una simulación de farmacia real con múltiples terminales. Ni estos recorridos ni las pruebas unitarias sustituyen revisión legal, hardware físico, proveedores de registros ni un piloto de farmacia en producción.

`operator-journeys.json` es el índice ejecutable de once recorridos que definen un turno: primera venta, carrito suspendido, pago dividido, aprobación de gerente, reembolso, cierre ciego de caja, cierre diario firmado, recepción de compra, transferencia entre sedes, cambio seguro de operador y un día minorista completo. Cada entrada posee un archivo/título exacto de Playwright y declara cobertura de rol, idioma, viewport, interacción y continuidad. `scripts/check-operator-journeys.mjs`, invocado por `ci:web`, falla cuando desaparece una prueba indexada, su título cambia sin actualizar el contrato, se elimina un recorrido obligatorio o la matriz pierde una variante operativa requerida. El contrato indexa flujos reales; no reemplaza su ejecución en navegador.

El recorrido de día minorista demuestra conciliación entre módulos. Desde el navegador real realiza conteo ciego y aprobación, crea/envía/recibe un borrador de reposición, abre asistencia y caja, suspende entre recargas un carrito de dos unidades, lo cobra, devuelve una unidad después de un relevo de gerente, registra y liquida la factura del proveedor, transfiere una unidad a otra sede, cierra la caja y el día, vuelve a recargar y verifica existencias finales por sede y agregadas respaldadas por SQLite. Paquetes reales independientes mantienen el mismo núcleo minorista calificado para seguimiento de lotes alimentarios, procedencia serializada de compra/venta/devolución/transferencia y ventas de hijos de variantes Talla x Color. Esos paquetes no afirman pedidos automáticos ni conciliación externa de proveedores. El recorrido compartido independiente de conteo por identidad ejercita cantidades de lotes y escaneos de series tanto en web como en Electron.

El esquema v3 también selecciona evidencia real de UX agregada para creación de producto, primera venta, cierre firmado, recepción de existencias y recuperación operativa. Los recorridos referenciados de Playwright deben comprobar la ruta actual, un primer control utilizable concreto y el payload `observability.reportTaskMeasurement` emitido por el navegador, incluidos retrocesos esperados y errores de validación/recuperación. El helper E2E observa la solicitud tRPC real en vez de depender de la consulta de persistencia, por lo que la prueba sigue ejecutándose cuando un tenant optó por no almacenar métricas agregadas. Estas señales deterministas detectan montaje de rutas roto, primeras acciones inaccesibles, pérdida de comentarios de validación y bucles de recuperación; no afirman un estudio moderado de usabilidad ni cobertura real de NVDA en Windows.

El mismo contrato selecciona un recorrido ejecutable para cada área crítica del turno bajo `criticalE2E`: primera venta para vender, aprobación exacta del gerente para control, cierre diario firmado inmutable para cierre y transferencia entre sedes con diferencias para existencias. Esas cuatro pruebas llevan la etiqueta Playwright `@critical` y se ejecutan serialmente mediante `pnpm run test:e2e:web:critical`. El verificador mantiene el subconjunto en cuatro o menos, rechaza áreas faltantes o cambios de etiqueta e impide que un quinto recorrido etiquetado amplíe silenciosamente el presupuesto de CI. CI web en push y pull requests ejecuta este subconjunto acotado después de `ci:web`; la suite completa del navegador sigue siendo el requisito local para cualquier flujo afectado de inicio de sesión, ventas, inventario, importación o navegador.

El contrato opcional `test:e2e:web:soak` mantiene vivo un renderer autenticado en vez de recargar entre recorridos. Después de cinco ciclos de calentamiento ejercita creación/detalle de productos, historial de ventas, transiciones de rutas y sus ciclos de consultas durante 30 ciclos medidos. Cada punto de control fuerza GC de Chromium y registra heap JS usado y conteos de documentos, nodos DOM y listeners activos; solo se controla el crecimiento retenido final menos la línea base, porque un pico transitorio no es una fuga. La misma prueba en ejecución cierra el diálogo OCR de compras mientras la persistencia de carga se mantiene deliberadamente en curso y comprueba que se revoque su URL exacta de previsualización Blob antes de completar la respuesta tardía. La suite normal del navegador excluye `@long-shift-soak`; `ci:web` sigue ejecutando el comparador puro de crecimiento y el contrato de comando/presupuesto.

El contrato de recuperación operativa está definido en `packages/shared/src/operational-readiness.ts`. Cubre sincronización, entrega fiscal, hardware de recibos, pagos electrónicos, respaldo cifrado y actualizaciones de escritorio. `scripts/check-operational-readiness.mjs`, invocado por la validación web de CI, falla si un servicio pierde su propietario explícito, objetivo de respuesta, umbral, ancla de runbook, ruta de recuperación o título exacto de ejercicio ejecutable. El smoke de Operaciones verifica que el mismo contrato sea visible en inglés y español y que las acciones de recuperación lleguen a la superficie responsable. También inserta un incidente real de pago rechazado en outbox, lo reintenta como administrador, verifica el evento de auditoría y estado sin fallo y confirma en el navegador que baja el conteo invalidado de elementos que requieren atención. El mismo ejercicio demuestra que la medición agregada registra un éxito `recover_operation` con resultado exitoso de recuperación. Esto fija el ciclo señal → acción → mutación → resultado medido → cola renovada, más allá de la navegación.

Los overrides exactos de registro se revisan como excepciones explícitas y temporales, no como decoración permanente del lockfile. La política vincula selector y destino, exige responsable, justificación, criterios de eliminación y plazo por categoría, y falla de forma segura tras 14 días para techos de regresión, 30 días para mínimos de seguridad o deprecación y 90 días para fijaciones de compatibilidad. Una revisión elimina un override innecesario o renueva su evidencia y plazo solo después de que aprueben `pnpm run ci:audit` y la validación de runtime correspondiente. Los reemplazos locales `file:` son paquetes mantenidos del workspace y no deuda de fijación de versiones.

El alcance de auditoría se deriva de rutas, nunca del nombre de paquete ni de su alcance de desarrollo declarado. El wrapper obtiene el informe completo de avisos de pnpm y construye grafos de producción desde las raíces del bundle web, servidor independiente y Electron empaquetado. Los hallazgos se cotejan con la versión instalada vulnerable antes de rotularlos como alcanzables en runtime, no alcanzables en runtime o desconocidos. El contrato Electron fija explícitamente la ruta distribuida `@puntovivo/desktop → electron-updater → js-yaml` y rechaza Electron Forge en el grafo de producción de escritorio. Todo aviso de severidad baja o superior hace fallar CI, incluidos los de herramientas, y cualquier ambigüedad de registro, JSON, grafo o versión provoca fallo seguro.

La etiqueta no alcanzable en runtime por sí sola tampoco permite ignorar un aviso: es un resultado conservador del grafo de manifiestos. Ahora es la condición previa para la única excepción legítima, una disposición con vencimiento registrada en `config/audit-dispositions.json` y descrita en [SECURITY.md](SECURITY.md). La auditoría rechaza una disposición cuyo aviso clasifica como alcanzable en runtime o desconocido, cuyo paquete no coincide o cuya fecha de revisión venció, y falla si una disposición sobrevive al aviso que cubre. El argumento de bundle/importación y artefacto empaquetado sigue siendo una afirmación humana registrada y acotada por el plazo de revisión, no una demostración automatizada, porque la auditoría se ejecuta antes de que exista una compilación para inspeccionar.

## Requisitos adicionales del candidato a versión

Las validaciones automatizadas son necesarias pero insuficientes para una versión de escritorio. Un candidato también necesita:

- validación manual de paquetes en Linux, macOS y Windows;
- verificación de firma y notarización donde haya credenciales;
- instalación limpia y actualización desde la versión anterior de producción;
- comprobaciones de migración de base y rechazo de versión anterior;
- ensayo de respaldo y restauración con volumen de datos equivalente a producción;
- comprobaciones de impresora, cajón, escáner y terminal para cada dispositivo admitido;
- revisión de limitaciones conocidas en `PROJECT-STATUS.md` y notas de versión.

El workflow manual **Build Desktop** solo acepta un SHA completo de commit de candidato de 40 caracteres. Cada plataforma seleccionada obtiene ese commit exacto. Una compilación completa limpia la salida de paquetes, crea el instalador de la plataforma, ejecuta el smoke completo del runtime empaquetado (incluida la estructura de módulos nativos), ejecuta un recorrido de primer inicio de sesión del renderer empaquetado, realiza la recuperación cifrada dentro del binario Electron empaquetado y carga:

- el instalador exacto `Puntovivo-<version>-<os>-<arch>`;
- su blockmap cuando electron-builder emite uno;
- el feed de actualización `latest*.yml` correspondiente;
- `packaged-recovery-<os>[-<mac-generation>]-<short-sha>.json`;
- `candidate-evidence-<os>[-<mac-generation>]-<short-sha>.json`.

El manifiesto vincula el SHA del candidato con versión exacta del paquete, plataforma, arquitectura, versión real del SO host, destino de soporte estable, nombres de artefactos, tamaños en bytes, checksums SHA-256 y referencia coincidente al feed de actualización. La evidencia macOS usa nombres distintos para Sequoia y Tahoe para no presentar un resultado de Tahoe como compatibilidad con Sequoia. También recalcula SHA-512 y tamaño del instalador y exige que coincidan con los valores que verificará electron-updater. La recolección falla si el checkout difiere del SHA solicitado, falta el instalador/feed esperado, el feed apunta a otra versión, sus metadatos de integridad difieren del instalador o no aprobó el smoke de estructura, runtime o renderer empaquetados. También falla salvo que el informe de recuperación empaquetada pertenezca al mismo SHA, versión, plataforma y arquitectura y apruebe cada comprobación descrita abajo. El recorrido del renderer es obligatorio en Linux, macOS y Windows. Demuestra origen personalizado seguro del renderer, puentes preload, acceso API integrado, autenticación de primer uso y pantalla inicial poslogin respaldada por datos. Usa una clave SQLCipher aleatoria por ejecución y un almacén temporal de credenciales Chromium para que la automatización UI no dependa de prompts del llavero del runner; el smoke separado de runtime sigue ejercitando el arranque normal con almacén de claves del SO. Este contrato de nombres exactos impide presentar salida local obsoleta como evidencia actual.

La confianza de distribución ahora se mide. En macOS el recolector ejecuta las herramientas del propio host contra el bundle empaquetado — `codesign --verify --deep --strict`, `xcrun stapler validate` y `spctl --assess` — y registra uno de cuatro veredictos junto con evidencia por comprobación:

- `trusted` — firmado, notarizado y aceptado por Gatekeeper.
- `signed-not-notarized` — firma válida sin ticket adjunto. Esto es lo que produce el workflow manual, porque firma ad hoc para que el smoke de runtime pueda iniciar la app y nunca carga credenciales de firma de versiones.
- `untrusted` — no se verificó la firma o la herramienta no pudo responder. Una herramienta ausente se registra como desconocida y nunca cuenta como aprobación.
- `unsupported-platform` — Linux y Windows, cuyos modelos de confianza no evalúa este recolector. Se informa como estado propio para no confundirlo con aprobación ni fallo; verifica esos hosts por separado con el verificador de firmas de Windows antes de aceptar un candidato.

El veredicto se informa, no se impone: una compilación manual no confiable es el resultado esperado y no debe hacer fallar la recolección. Solo `trusted` en cada plataforma requerida supera el control de versión, y alcanzarlo requiere el workflow de versiones con material Developer ID real; la firma ad hoc sigue siendo solo validación.

Ejecuta `pnpm run rehearse:upgrade-recovery` para el requisito de migración de base. Construye un fixture cifrado verificado v1.7.0 con dos grafos de tenant, lo actualiza a través del journal vigente, verifica un segundo arranque idempotente e inicia el contrato de compilación histórica en un proceso aislado para demostrar que se rechaza una versión anterior sin modificar la base. Luego agrega centinelas de esquema actual de asistencia, aprobación, privacidad, personal e inventario serializado; crea un ZIP cifrado en formato de producción; lo extrae en otro directorio de instalación; cambia la clave de la base preparada a una clave nueva de instalación; y arranca la base restaurada mediante el servidor real.

El informe demuestra huellas históricas y de dominios actuales, separación de tenants, conservación de identidad de dispositivo, separación de claves en ambos sentidos, inmutabilidad de la base de origen, tamaño/hash del bundle, hora de instantánea y tiempos de respaldo/restauración. El comando escribe el informe sanitizado en el directorio ignorado `.artifacts/recovery-rehearsal/`; consérvalo con la evidencia del candidato. El informe nunca debe contener claves SQLCipher, credenciales, identificadores de dispositivo, rutas absolutas ni filas comerciales sin procesar.

### Evidencia de recuperación cifrada empaquetada

El workflow manual completo **Build Desktop** ejecuta el modo de solo recuperación del ejecutable real empaquetado en cada sistema operativo seleccionado. No ejecuta el ensayo Node desde el código ni abre la base del operador. El wrapper del host crea almacenamiento temporal aislado, inicia el paquete con una bandera explícita de autorización de recuperación, valida el informe resultante, copia solo ese informe sanitizado a `out-builder` y elimina la instalación temporal.

El perfil inmutable `retail-annual-medium-v1` representa un año de una sede minorista activa: 2,500 productos, 10,000 clientes, 365 sesiones de caja cerradas, 50,000 ventas completadas, 150,000 líneas de venta y 50,000 filas de pago. El paquete debe:

1. crear el esquema actual desde sus migraciones empaquetadas y sembrar el perfil completo en una base SQLCipher;
2. crear y comprobar la integridad del formato ZIP de respaldo de producción;
3. rechazar una clave de cifrado ajena sin modificar la instantánea válida;
4. rechazar un ZIP cuya entrada de base cifrada se haya truncado;
5. restaurar y cambiar la clave en una instalación independiente, luego arrancar esa copia mediante el grafo del servidor empaquetado;
6. calcular huellas de cada fila comercial representativa antes y después de restaurar;
7. demostrar que el hash de bytes de la base original no cambió tras recuperar;
8. registrar versión de app, versión de esquema, plataforma, arquitectura, tiempo de recuperación y edad de la instantánea sin rutas, claves, credenciales, identidades de dispositivo ni filas comerciales.

Para un paquete ya compilado en el host actual, ejecuta:

```bash
pnpm run rehearse:packaged-recovery -- \
  --against-packaged apps/desktop/out-builder \
  --candidate-sha "$(git rev-parse HEAD)" \
  --output .artifacts/packaged-recovery/current-platform.json
```

Una aprobación local demuestra solo ese paquete y host. La preparación multiplataforma sigue exigiendo una ejecución completa y nueva del workflow para Linux, macOS y Windows contra el mismo SHA de 40 caracteres. No copies informes entre plataformas ni conviertas un ensayo desde el código en evidencia empaquetada.

La línea base histórica documentada de recuperación cifrada multiplataforma es el workflow manual [ejecución 31264233582](https://github.com/johnny4young/puntovivo/actions/runs/31264233582) del 2026-08-08 contra el candidato publicado `c6aebb8ee27e1f6f73e593cbd0a4ff117fd8a567` (app `1.10.1`, esquema de base `35`). Linux x64, macOS arm64 y Windows x64 aprobaron creación del paquete, smokes nativos/runtime y renderer de primer login, y las nueve comprobaciones de recuperación cifrada sobre el perfil de 262,865 filas. Los manifiestos descargados se revalidaron contra hashes de sus instaladores, feeds e informes reales; cada uno rechazó clave incorrecta y bundle corrupto, conservó la base de origen y arrancó la copia restaurada. Son artefactos manuales de candidato solo para validación: demuestran comportamiento de runtime y recuperación, no firma de versión, notarización, certificación ni compromiso de tiempo de recuperación de producción. El job macOS se ejecutó en Tahoe 26.5.2 arm64. No sustituye una ejecución Sequoia independiente ni las comprobaciones de instalación limpia, actualización real y rechazo de versión anterior en máquina representativa requeridas antes de promover el despliegue.

Una [ejecución manual posterior de compilación para cuatro destinos](https://github.com/johnny4young/puntovivo/actions/runs/34649168839) aprobó el 2026-09-11 para el commit de rama `ef85c941`, no un candidato a versión. Empaquetó, ejecutó smokes y ensayó recuperación cifrada en Linux, Windows, Sequoia y Tahoe. Es anterior a la publicación de v1.14.4 y no puede usarse como evidencia Gate 5 de esa versión. Ninguna de las dos ejecuciones conserva artefactos descargables, por lo que ambas son registros históricos y no evidencia inspeccionable. El [workflow de versión v1.14.4](https://github.com/johnny4young/puntovivo/actions/runs/35138577582) aprobó el 2026-09-16 y publicó artefactos de plataformas y un feed de actualización; tampoco establece Gate 5 en máquinas representativas.

## Gate 5 en máquinas representativas

Gate 5 queda deliberadamente fuera de CI alojado en GitHub. Cada plataforma distribuida y destino de soporte necesita su propio manifiesto; un candidato aprueba ese destino solo cuando una máquina representativa conserva evidencia vinculada por hashes de todas estas observaciones contra el mismo UUID de sesión, plataforma, arquitectura, versión observada del SO, versión de app y SHA completo del candidato:

1. instala el candidato firmado en un perfil de SO nuevo y aislado sin datos previos de usuario de Puntovivo, inícialo y captura la versión observada;
2. instala la versión firmada anterior admitida en otro perfil aislado, crea un canario determinista, recibe el candidato mediante la ruta de producción `electron-updater`, reinicia, observa versión del candidato e historial de actualización y exporta el mismo canario antes y después;
3. intenta el instalador firmado anterior admitido y conserva su rechazo visible más instantáneas cifradas de la base cerrada/con checkpoint idénticas byte por byte antes y después del intento. Las pruebas deterministas del actualizador cubren la política regresiva normal/rollback del appcast; la recuperación manual por instalación de emergencia sigue siendo un ejercicio separado del operador;
4. ejecuta todos los recorridos Electron desde una terminal interactiva independiente contra un checkout completamente limpio de ese candidato exacto; y
5. haz que alguien con rol de operador de versiones revise de forma independiente capturas distintas de instalación limpia, actualización y rechazo de versión anterior.

No realices ninguno de estos pasos contra el perfil de producción de un operador. Usa una cuenta del SO o imagen de máquina desechable y cierra Puntovivo antes de copiar la base cifrada. Conserva capturas y bases sin procesar localmente bajo el árbol ignorado `.artifacts/`; el manifiesto sanitizado contiene únicamente nombres de archivo, conteos de bytes, hashes, etiquetas acotadas de host, observaciones y una etiqueta no personal de rol de revisor.

El comando externo de Electron rechaza shells no interactivos y cualquier señal de CI, Codex, XCTest, inyección de bibliotecas dinámicas o worktree sucio. Es un límite de evidencia, no una solución alternativa para pruebas fallidas:

Genera un ID nuevo de correlación con `node -p "crypto.randomUUID()"` y usa ese UUID exacto tanto en el comando externo como en el borrador de Gate 5:

```bash
pnpm run test:e2e:electron:external -- \
  --candidate-root /absolute/path/to/clean-candidate-worktree \
  --packaged-app /absolute/path/to/the/installed/signed/Puntovivo.app \
  --session-id 018f6f8c-4e5b-7a21-8abc-1234567890ab \
  --output .artifacts/gate5/macos-sequoia/external-electron.json
```

`--candidate-root` permite que las herramientas actuales orquesten un checkout de versión histórica sin modificarlo; `--packaged-app` hace que Playwright maneje el candidato firmado instalado mediante la ruta CDP empaquetada en lugar de iniciar el bundle Electron de desarrollo. En el host representativo, coloca ambos instaladores firmados, las tres capturas distintas, exportaciones de canario antes/después, instantáneas cifradas de base antes/después y `external-electron.json` en un directorio de sesión. ## Informe de fallos

Registra comando exacto, runtime, sistema operativo, prueba fallida y si el fallo provino del código del proyecto o del entorno de ejecución. No informes una validación aprobada cuando se omitió, interrumpió o reemplazó por una prueba de menor alcance.

## Contratos de regresión de reservas, entregas e inbox firmado

Las suites de cumplimiento distinguen intención operativa de autoridad financiera:

- `reservations.test.ts` y las suites de ventas de restaurante cubren capacidad de mesas, solapamientos, vínculo explícito de versión/grupo de reserva, entradas heredadas y reverificaciones de elegibilidad bajo el bloqueo de escritura.
- `deliveryOrders.test.ts` cubre transiciones estrictas, validación de repartidor/motivo, propiedad de venta, rechazo de venta reembolsada, repetición y rollback transaccional.
- `external-orders.test.ts` cubre ingreso firmado, identidad nonce/evento, cancelación reordenada, aceptación del catálogo local y reversión financiera explícita.
- `external-order-upgrade.test.ts` migra bases históricas y reabre archivos en texto plano y SQLCipher conservando credenciales selladas y evidencia exacta de inbox/recibo/nonce/transición. Una segunda conexión SQLite real mantiene el bloqueo de escritura para ejercitar fallo seguro y reintento exacto tras liberar el bloqueo. `delivery-upgrade.test.ts` conserva campos heredados de entrega sin inventar procedencia.
- `external-order-simulator-cli.test.ts` ejecuta la CLI real contra un endpoint loopback. Un estado HTTP exitoso debe incluir un recibo válido para el evento/pedido enviado; JSON arbitrario y el recibo de otro pedido fallan.
- Las pruebas web `delivery.spec.ts`, `reservations.spec.ts` y `external-orders.spec.ts` ejecutan rutas reales de UI y API y concilian sus propios registros SQLite aislados. Las credenciales del conector nacen en la UI; el cliente sandbox envía eventos firmados exactos por HTTP. El fixture fraccionario declara tanto paso como mínimo. La aserción móvil comprueba límites visibles del diseño tras redimensionar, no solo desbordamiento del documento (de otro modo el contenido recortado podría dar una aprobación falsa). El solapamiento de reservas se rechaza mediante el diccionario real de errores cargado bajo demanda. La navegación al detalle de venta ocurre una sola vez y no debe reabrir el diálogo tras recargar. ### Recuperación de autenticación y carreras de respuestas tardías

Las suites enfocadas de autenticación ejercitan recuperación bloqueada tras límites de solicitudes de salud, renovación y verificación de identidad, interrupciones de servicio y pérdida de red. Los períodos de espera requieren un reintento explícito, la UI vinculada a la identidad permanece ausente y los carritos conservan su propietario original. Las pruebas de respuestas diferidas cubren renovación del renderer, verificación de token de escritorio y escrituras de estado sellado Hub frente a limpieza, login de reemplazo y renovación concurrente. Un éxito o rechazo tardío no debe instalar, devolver ni eliminar la autoridad de otro operador.

Los recorridos de recuperación web y Electron inyectan deliberadamente un fallo de transporte antes de reintentar contra la autoridad real y recargar el carrito restaurado. Web cubre EN/ES y verifica existencias SQLite sin cambios; Electron usa la ruta real de reanudación de main y productos creados desde UI. Otro recorrido del navegador conserva la cookie httpOnly anterior, elimina su par CSRF, elige reingreso explícito y exige bootstrap seguro antes de un login nuevo. Estos fallos inyectados no afirman un recorrido real de agotamiento del límite de solicitudes: la suite de transporte del servidor fija por separado el predeterminado de producción de 100 solicitudes y la política de origen/encabezados. No se agrega excepción global de consola o respuestas para estos escenarios; solo el límite inyectado único es aceptado por su propio recorrido.

Los recorridos de cambio de contraseña ejecutan el diálogo diferido de cuenta, inician sesión con la credencial nueva y recargan. Electron comprueba además que el puente real de reanudación no devuelva token entre revocación y reingreso y vuelva a recibir un token verificado después de un login nuevo. Las pruebas del proveedor cubren comandos rechazados, finalización tardía después de otro login, limpieza de credenciales selladas y fallos de almacenamiento. Las pruebas del store real del carrito demuestran que su restablecimiento en memoria precede a una escritura fallida de persistencia. Las pruebas de medición de tareas cubren entrega al propietario actual y suprimen muestras anónimas, de identidad reemplazada y lotes en cola después de revocación. Las pruebas normales de cierre de sesión también mantienen su respuesta pendiente y comprueban cercado de limpieza de tareas antes de desmontar, sin borrar el bearer necesario para aparcar trabajo del servidor. Las respuestas tardías de renovación no pueden reinstalar credenciales durante ese cierre pendiente. Las aserciones HTTP/consola siguen siendo estrictas.

Las suites de almacenamiento y actualización cubren límites de enteros seguros, evidencia heredada que admite nulos, pares coherentes cantidad/valor, bases históricas en texto plano y cifradas, conservación de claves foráneas, identificadores de filas FTS y triggers restaurados.

`e2e/web/inventory-tracking-value.spec.ts` ejercita el editor real EN/ES de productos y las superficies de lectura de inventario mediante UI, tRPC, SQLite y recarga. Demuestra que saldos opuestos por sede no pueden ocultarse tras un total global cero, que el operador ve textos traducidos de conflicto que permiten actuar y que los centavos de lotes adoptados y el cero conocido no se reconstruyen desde costos unitarios redondeados.
`e2e/web/sync-inventory-policy.spec.ts` verifica que los incidentes bloqueados de recuperación conserven su evidencia y expongan solo acciones autorizadas por el servidor.

Estas pruebas califican los flujos locales ejercitados, no sincronización remota multimaestro, instalación firmada, hardware ni certificación regulatoria. Las ejecuciones nuevas deben identificar su candidato; los logs históricos exitosos no validan un checkout reconstruido o editado después.
