# Accesibilidad (WCAG 2.2 AA)

**Idioma:** Español · [English](../A11Y.md)

> Estado: motor implementado (helper de axe-core + controles de contraste y modos adaptativos + revisión representativa en navegador).

Este documento explica cómo Puntovivo aplica controles de accesibilidad en CI y en la validación local de versiones, y qué hacer cuando un componente nuevo falla un control. Se aplica el mismo principio que al mínimo de cobertura y los presupuestos de rendimiento: cada regresión es una decisión deliberada, documentada en el mismo PR que la produce.

WCAG 2.2 AA es el objetivo de accesibilidad. El conjunto predeterminado de etiquetas automatizadas de axe es `wcag2a` + `wcag2aa`; estas comprobaciones y las pruebas representativas del navegador no establecen conformidad completa con WCAG 2.2 AA ni validación con un lector de pantalla nativo.

## Qué se controla hoy

| Superficie                                                                                                      | Dónde                            | Ejecutor del control                                                                    |
| --------------------------------------------------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- |
| Reglas WCAG 2 A + AA de axe-core a nivel de componente                                                          | Vitest                           | `assertNoA11yViolations(container)` de `apps/web/src/test/a11y.ts`                      |
| Contraste de tokens de color (`background/foreground`, `card/card-foreground`, `primary/primary-foreground`, …) | `ci:web`                         | `scripts/check-contrast.mjs` después del control de tamaño del bundle                   |
| Reglas de movimiento reducido y colores forzados de Windows                                                     | `ci:web`                         | `scripts/check-adaptive-ui.mjs` sobre el CSS compartido de Operator Deck                |
| Prueba básica de accesibilidad de Playwright en las rutas principales de usuario                                | Control E2E local para versiones | `runAxeOnPage(page)` de `e2e/web/support/a11y.ts`, ejecutado por `e2e/web/a11y.spec.ts` |

La prueba completa de `/sales` solo con teclado está implementada. Playwright también fija la semántica del navegador para la navegación adaptable del administrador y el panel de pago del cajero, un ancho de cobro equivalente al 200%, el movimiento reducido y los colores forzados simulados de Windows. Queda pendiente la revisión específica con NVDA real en Windows. Las declaraciones `aria-keyshortcuts` alineadas con el mapa de atajos están implementadas en `SalesCheckoutPanel` (Cobrar `F1`, Suspender `Mod+P`, Mostrar/ocultar suspendidas `Mod+R`).

Esta guía es la referencia canónica de accesibilidad para ingeniería, preventa, auditores y revisores no técnicos.

## Por qué importa la accesibilidad

Dos razones:

1. **Revisión y compras**: los pilotos empresariales pueden requerir evidencia de accesibilidad. Las comprobaciones automatizadas documentan las reglas y superficies probadas; no establecen cumplimiento legal ni certificación de accesibilidad.
2. **Operación**: los cajeros pasan el día en este producto. Un operador que usa solo teclado por una lesión de muñeca o un operador con baja visión que usa un lector de pantalla debe poder registrar una venta sin soluciones alternativas.

## Cómo se ejecutan los controles

### axe-core en pruebas de componentes

`apps/web/src/test/a11y.ts` exporta `assertNoA11yViolations(container, options?)`. Ejecuta `axe-core` sobre el subárbol renderizado con las reglas WCAG 2 A + AA y lanza un error ante cualquier infracción igual o superior al umbral de gravedad configurado (por defecto `serious`; puedes elegir `moderate` para superficies críticas).

Úsalo en cualquier prueba de componente que incluya campos de formulario, diálogos, botones que solo tengan iconos o widgets interactivos:

```ts
import { assertNoA11yViolations } from '@/test/a11y';

it('passes axe-core WCAG 2 AA on the happy-render path', async () => {
  const { container } = render(<MyComponent />);
  await assertNoA11yViolations(container);
});
```

El helper es optativo: las pruebas existentes siguen pasando hasta que lo incorporan. Agrega la llamada cuando trabajes en una superficie nueva de la interfaz.

Para elevar la exigencia de una pantalla crítica (cobro, inicio de sesión, ajustes):

```ts
await assertNoA11yViolations(container, { severityFloor: 'moderate' });
```

### Control de contraste

`pnpm run ci:web` ejecuta las comprobaciones compartidas, la política completa de auditoría de dependencias, lint rápido, comprobación de tipos, lint del workspace, pruebas de cobertura y compilación de producción. Luego ejecuta las pruebas de contrato de los scripts, los controles de modos adaptativos, tamaño del bundle y contraste, las comprobaciones de adopción y recorridos de Operator Deck y el control medido de Lighthouse. El `package.json` raíz es la fuente de verdad del orden completo.

`node scripts/check-contrast.mjs` analiza los ámbitos CSS de `apps/web/src/styles/theme.css`, resuelve alias de tokens, convierte valores opacos `oklch(L C H)` a sRGB lineal y calcula la luminancia relativa WCAG y las relaciones de contraste de los pares controlados.

Los pares controlados son:

- `background` / `foreground`
- `card` / `card-foreground`
- `popover` / `popover-foreground`
- `muted` / `muted-foreground`
- `accent` / `accent-foreground`
- `primary` / `primary-foreground`
- `secondary` / `secondary-foreground`
- `destructive` / `destructive-foreground`
- `background` / `muted-foreground` (entre superficies)
- `card` / `muted-foreground` (entre superficies)
- `popover` / `muted-foreground` (entre superficies)
- `operator-positive-control` / `operator-semantic-control-foreground`
- `operator-critical-control` / `operator-semantic-control-foreground`
- `operator-info-surface` / `operator-info-ink`
- `operator-positive-surface` / `operator-positive-ink`
- `operator-warning-surface` / `operator-warning-ink`
- `operator-critical-surface` / `operator-critical-ink`
- `warning-50` / `warning-700` (superficie badge-warning)

El mínimo por defecto es **4.5:1** (WCAG AA para texto de cuerpo). Los estilos de botón compartidos de Puntovivo usan `text-sm font-semibold`, así que los pares `primary` y `destructive` también usan el mínimo de texto de cuerpo, en lugar de la regla menos exigente para texto grande.

La validación de temas falla si no puede comprobar el contrato:

- Deben existir tanto `:root` como `.dark`. Los ámbitos repetidos se combinan en orden de aparición y el modo oscuro hereda las declaraciones raíz antes de aplicar las sobrescrituras posteriores.
- Cada par controlado de ambos temas efectivos debe poder medirse. Los tokens faltantes, alias sin resolver, colores no compatibles, valores translúcidos y conversiones no finitas hacen fallar el control.
- Otros ámbitos CSS pueden informar advertencias por pares faltantes o no compatibles; se omiten los ámbitos sin declaraciones relevantes. Estas advertencias no debilitan el contrato obligatorio de los temas claro/oscuro.

## Cómo corregir una regresión de contraste

1. Abre `apps/web/src/styles/theme.css`. Encuentra la declaración que falla en el ámbito `:root` o `.dark`.
2. Ajusta `oklch(L C H)` hasta alcanzar el mínimo de contraste:
   - Para pares de texto de cuerpo, oscurece el primer plano (menor L) o aclara el fondo (mayor L) hasta que la relación sea ≥ 4.5.
   - Verifica localmente con `node scripts/check-contrast.mjs`: la salida PASS muestra la relación resultante.
3. Incluye el cambio en el PR que produjo la regresión. El control sigue pasando.

Si la regresión es intencional y necesitas justificadamente reducir el mínimo (por ejemplo, una variante de botón nueva que solo muestra texto grande), actualiza `PAIR_FLOOR_OVERRIDES` en `scripts/check-contrast.mjs` con un comentario que explique el motivo.

## Cómo silenciar una sola infracción de axe

A veces una infracción es un falso positivo (axe encuentra un `role` que no espera; la superficie intencionalmente no es interactiva). Hay dos opciones:

1. **Limita la aserción** a un subárbol que sabes que es correcto:

   ```ts
   await assertNoA11yViolations(container.querySelector('[data-testid="happy-path"]')!);
   ```

2. **Configura la ejecución** para excluir la regla que falla con un comentario explícito:

   ```ts
   await assertNoA11yViolations(container, {
     runOptions: {
       runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa'] },
       rules: {
         // The role here is intentional — see ADR-0009.
         'aria-allowed-role': { enabled: false },
       },
     },
   });
   ```

El comentario es obligatorio: un revisor debe poder entender por qué la supresión es legítima sin consultar al autor original.

## Cómo agregar un par nuevo al control de contraste

1. Abre `scripts/check-contrast.mjs` y agrega el par a `ENFORCED_PAIRS`.
2. Si el par solo se usa para texto grande, agrega una entrada a `PAIR_FLOOR_OVERRIDES` con el mínimo de 3:1.
3. Ejecuta `node scripts/check-contrast.mjs` para confirmar que el par pasa.

## Convenciones ARIA de este código

Patrones que los revisores deben comprobar en cada PR que modifica la interfaz:

- **Botones que solo tienen iconos**: deben declarar `aria-label` (o `aria-labelledby` que apunte a una etiqueta visible). Los botones `Bell`, `User`, `Menu`, etc. de `Header.tsx` y `Sidebar.tsx` siguen este patrón.
- **Widgets desplegables** (secciones plegables, menús, popovers): declaran `aria-expanded` y `aria-controls` apuntando a la región que muestran. El despliegue de secciones en `Sidebar.tsx` es la referencia.
- **Menús abiertos desde un botón**: declaran `aria-haspopup="menu"` en ese botón.
- **Modales**: usan el componente compartido `Modal`, que ya implementa confinamiento del foco, manejo de ESC y devolución del foco al control de apertura. Los diálogos nuevos deben reutilizarlo.
- **Colores de estado**: deben acompañarse de texto o un icono para que el significado sea visible sin color (`status pill` con etiqueta de texto, `KdsOrderCard` con etiqueta de temporizador, …).

## Prueba básica de accesibilidad con Playwright

`e2e/web/a11y.spec.ts` ejecuta axe-core en Chromium real sobre las rutas principales de usuario después de un inicio de sesión real. Cada prueba inicia sesión con el rol correspondiente a la ruta (`anon` para `/login`, cajero para la superficie de cajero de `/sales`, gerente para cuentas de proveedores y administrador para las demás superficies administrativas), espera un encabezado canónico o un botón de acción principal para que axe analice un DOM estable y comprueba el mismo contrato WCAG 2 A + AA con umbral serious del helper de pruebas de componentes. `ClientIssueTracker` de Playwright, ya presente en `e2e/web/support/app.ts`, también aplica la invariante de cero errores de consola; la prueba falla tanto por infracciones de axe como por errores de runtime emitidos durante el renderizado de la página.

El catálogo actual contiene veintiuna entradas. Cada una comprueba el umbral serious de WCAG 2 A + AA; la lista describe la cobertura, no una ejecución de validación nueva:

- `/login` (anónimo) — cubierta
- `/dashboard` (administrador) — cubierta
- `/sales` (cajero) — cubierta
- `/sales` (administrador) — cubierta
- `/inventory` (administrador) — cubierta
- `/customers` (administrador) — cubierta
- `/products` (administrador) — cubierta
- `/purchases` (administrador) — cubierta
- `/orders` (administrador) — cubierta
- `/provider-payables` (gerente; cuenta de proveedores sin CRUD de proveedores) — cubierta
- `/quotations` (administrador; el módulo `quotations` está activado por defecto) — cubierta
- `/promotions` (administrador) — cubierta
- `/company` (administrador) — cubierta
- `/data-import` (administrador) — cubierta
- `/audit-logs` (administrador) — cubierta
- `/day-close` (administrador) — cubierta
- `/touch` (administrador; módulo `pos-touch`) — cubierta
- `/kds` (administrador; módulo `kds`) — cubierta
- `/customer-display` (prueba de administrador; todos los roles de ventas están autorizados; módulo `customer-display`) — cubierta
- `/m` (administrador; módulo `mobile-waiter`) — cubierta
- `/delivery` (administrador; módulo `delivery`) — cubierta

El contenedor compartido `DataTable` permite desplazamiento horizontal con teclado mediante `tabIndex={0}`, `role="region"` y `aria-label={t('table.scrollableLabel')}`. La etiqueta localizada es `common:table.scrollableLabel`; las pruebas de componentes fijan `tabindex='0'`, `role='region'` y la presencia de `aria-label`.

Las superficies condicionadas por módulos (`/touch`, `/kds`, `/customer-display`, `/m`, `/delivery`) están cubiertas. La base E2E fuerza la activación de sus módulos mediante `ensureModulesEnabled` en `e2e/shared/baseline.ts` (la misma escritura `json_set` de `$.modules.<id>` que realiza la mutación `modules.setActive`), para que `SurfaceShellRoute` renderice cada superficie en lugar de redirigir a `/dashboard` y axe analice el DOM real. El administrador accede a las cinco (está en `salesRoles` y `managerOrAdminRoles`). Con los datos de prueba de comercio minorista, las superficies muestran sus estados vacíos / de marcador de posición (sin tickets de cocina ni pedidos de entrega); el catálogo comprueba el umbral serious en esos estados representativos; los flujos operativos con datos necesitan su propia evidencia de validación.

### Ejecución local

```
# Boots dev:server + dev:web via the playwright webServer block and
# runs the a11y suite end-to-end:
pnpm run test:e2e:web -- a11y.spec.ts
```

Fallos que la prueba informa claramente:

- Una infracción de axe de nivel `serious` o superior: el mensaje enumera cada regla que falla, el selector afectado, la URL de ayuda WCAG y el resumen del fallo de axe.
- Un error de consola o respuesta de red 4xx / 5xx durante el renderizado: `ClientIssueTracker` lo recopila y `expectNoClientIssues` comprueba que la lista esté vacía.

### Cómo corregir una regresión

1. Reproduce localmente: `pnpm run test:e2e:web -- a11y.spec.ts`.
2. Abre el resumen del fallo: axe apunta al selector exacto que falló (`button:not([aria-label])`, `label[for]=missing`, …).
3. Corrige el archivo fuente al que corresponde el selector. Las causas más comunes son: un `<button>` que solo tiene un icono sin `aria-label`, un `<select>` renderizado como popover personalizado sin `aria-haspopup`, un salto de jerarquía de encabezados (de `<h1>` directamente a `<h3>`), un `<input>` sin `<label htmlFor>` ni `aria-labelledby`.
4. Vuelve a ejecutar la prueba. La traza de `playwright-report/web/` contiene una instantánea del análisis de axe por prueba que ayuda cuando el fallo es intermitente.

### Cómo suprimir una sola regla

Se aplica el mismo contrato del helper de componentes: cada supresión lleva una justificación escrita que un revisor puede evaluar. Ejemplo:

```ts
await runAxeOnPage(page, {
  extraTags: [],
  // The role on the data-table header here is intentional; see
  // ADR-0009 for the reason we ship a custom grid.
  exclude: ['[data-testid="custom-grid-header"]'],
});
```

Usa `exclude` para supresiones por superficie y `runOptions.rules` a nivel de componente (en `assertNoA11yViolations`) para supresiones por regla. Nunca silencies una regla globalmente.

## Navegación con teclado por filas de tablas

Había una brecha importante de accesibilidad en el código: las tablas renderizaban filas `<tr>` solo con `onClick`, sin `tabIndex`, `onKeyDown` ni gestión del foco. Un cajero que usara solo teclado no podía seleccionar un producto, cliente o venta desde ninguna tabla; necesitaba el mouse.

`ProductSearchDialog` es la primera tabla que cerró esa brecha. El patrón es intencionalmente sencillo para aplicarlo a todas las tablas sin cambiar su semántica:

1. **Conserva la semántica de tabla**. NO agregues `role="listbox"` a `<tbody>` ni `role="option"` a `<tr>`. Las tablas de SKU + Nombre + Existencias + Precio + Unidad son datos en columnas reales: el `role="row"` implícito (que ya admite `aria-selected`) junto con un tabindex móvil es el patrón WAI-ARIA correcto.

2. **Tabindex móvil**. Mantén un estado `activeRowIndex` (por defecto `0`); cada fila renderiza `tabIndex={index === activeRowIndex ? 0 : -1}`. Solo la fila activa entra en el orden de Tab: el confinamiento del foco del Modal (cuya consulta de elementos enfocables incluye `[tabindex]:not([tabindex="-1"])`) omite automáticamente las filas inactivas sin conexiones adicionales.

3. **`aria-selected` refleja el estado de la aplicación**, no el foco móvil. La fila activa puede no ser la seleccionada (el cajero podría estar recorriendo resultados antes de presionar Enter en uno).

4. **Reinicia cuando cambian los elementos con el patrón setState en el mismo renderizado de React 19**, NO `useEffect`:

   ```tsx
   const [activeRowIndex, setActiveRowIndex] = useState(0);
   const [lastItemsKey, setLastItemsKey] = useState('');
   const itemsKey = items.map(item => item.id).join('\u0000');

   if (itemsKey !== lastItemsKey) {
     setLastItemsKey(itemsKey);
     setActiveRowIndex(0);
   }
   ```

   El setState condicional durante el renderizado encola un nuevo renderizado dentro del mismo ciclo y evita la regla de lint `react-hooks/no-state-update-in-effect`, que prohíbe renderizados en cascada. Consulta el patrón canónico en [react.dev — Quizás no necesites un efecto](https://react.dev/learn/you-might-not-need-an-effect).

5. **Asignaciones de teclas que reflejan CommandPalette**:
   - `ArrowDown` → `Math.min(index + 1, items.length - 1)` (sin volver al inicio; mantiene una memoria muscular coherente en el renderizador).
   - `ArrowUp` → `Math.max(index - 1, 0)` (sin volver al final).
   - `Home` → fila `0`.
   - `End` → fila `items.length - 1`.
   - `Enter` / `' '` (Espacio) → ejecuta el mismo callback de selección que el `onClick` existente. La ruta del mouse se mantiene intacta.
   - Cada tecla manejada llama a `event.preventDefault()`. Las demás se propagan para que sigan funcionando los atajos de documento (`Alt+U` para enfocar el selector de unidad, etc.).

6. **`onFocus` sincroniza `activeRowIndex`** cuando una fila recibe el foco por clic del mouse o de forma programática. Esto mantiene el tabindex móvil sincronizado con la fila que usa el cajero, independientemente del dispositivo de entrada.

7. **Estilos `focus-visible`, no `focus`**. La fila activa lleva `focus:outline-none focus-visible:bg-primary-50/60 focus-visible:ring-2 focus-visible:ring-primary-500/60`. El anillo aparece al navegar con teclado, pero no al hacer clic con el mouse, siguiendo la convención de la plataforma.

### Cómo aplicar el patrón a otras tablas

Hay dos superficies en el código: tablas que usan la primitiva compartida `DataTable` (la gran mayoría: `SalesHistoryTable`, `PurchasesHistoryTable`, `OrdersHistoryTable`, `QuotationsHistoryTable`, `CustomersPage`, `ProductsPage`, además del contenedor `ResourcePage` que aloja las listas de administración / ajustes), y tablas personalizadas que renderizan su propio `<table>` (hoy solo `ProductSearchDialog`). Cada superficie tiene su receta.

#### Consumidores de `DataTable`

`DataTable.tsx` ya controla el contrato completo de tabindex móvil (ArrowUp / ArrowDown / Home / End, además de `tabIndex` de `<tr>`, `aria-selected` y anillo `focus-visible`). Debes conectar la acción de activación de fila: lo que `Enter` y `Space` deben hacer sobre la fila enfocada:

```tsx
<DataTable
  columns={columns}
  data={items}
  // ...existing props
  onRowActivate={row => onView(row.id)}
/>
```

Elige la acción principal del mouse para la fila (Ojo / Ver, Lápiz / Editar, Abrir detalles) y pasa el mismo callback. La ruta de activación es incondicional: no requiere `enableRowSelection`, y la semántica de `onClick` del mouse se mantiene intacta.

Los consumidores que pasan por `ResourcePage` reciben la misma prop: este reenvía `onRowActivate` a su `DataTable` integrado.

Restricción por roles: cuando la acción principal está restringida por rol (por ejemplo, "Editar" solo para gerente / administrador), restringe la propia prop (`onRowActivate={canManage ? handleOpenEdit : undefined}`) para que la ruta de teclado refleje la disponibilidad del botón de la columna.

Pruebas: agrega un caso de regresión por consumidor que enfoque una fila y compruebe que el callback se ejecuta con el ID correcto. Sigue el patrón de `SalesHistoryTable.test.tsx`, `PurchasesHistoryTable.test.tsx`, `OrdersHistoryTable.test.tsx` y `QuotationsHistoryTable.test.tsx`.

#### `<table>` personalizado fuera de DataTable

Si la superficie renderiza su propio `<table>` (hoy solo `ProductSearchDialog`), sigue el patrón implementado en línea: estado `activeRowIndex` + `lastItemsKey`, `rowRefs`, handler `onKeyDown` en cada `<tr>`, etc. Consulta la implementación canónica en `apps/web/src/components/dialogs/ProductSearchDialog.tsx` y el patrón de pruebas en `ProductSearchDialog.test.tsx > keyboard navigation` (~13 casos).

Prefiere migrar la superficie a `DataTable` cuando sea viable: ProductSearchDialog conservó su diseño personalizado por el panel de selección derecho, pero la mayoría de las tablas simples pueden adoptar `DataTable` y heredar la compatibilidad con teclado.

## Prueba de `/sales` solo con teclado

`e2e/web/sales-keyboard-only.spec.ts` es la protección E2E permanente para el compromiso de uso del cajero principalmente con teclado, basada en el contrato de foco, la navegación por filas de ProductSearchDialog y la activación de filas de DataTable. La especificación recorre el flujo completo del cajero sin tocar el mouse:

1. **`base flows`** (4 casos): ida y vuelta del foco automático al montar, venta completa mediante F1 + Tab + Enter (con 3 análisis de axe en línea), efectivo exacto con F2 y comprobación del orden de tabulación con 12 pulsaciones desde el montaje de `/sales`.
2. **`quick-create + palette`** (3 casos): abrir/cerrar la paleta con Mod+K, crear rápidamente un producto durante una venta mediante la paleta y crear rápidamente un cliente durante una venta mediante la paleta.
3. **`cart manipulation`** (3 casos): F1 con carrito vacío sigue bloqueado por el panel de comprobación previa, Mod+Z deshace la última mutación del carrito y Enter en una fila de SalesHistoryTable abre el modal de detalle después de la venta (integración de activación de fila).

### Helper

`e2e/web/support/sales-keyboard.ts` exporta:

- `MOD_KEY`: reflejo de `'Meta' | 'Control'` según la plataforma de la resolución de Mod del catálogo.
- `SEARCH_INPUT_SELECTOR`: ID canónico del campo de búsqueda de `/sales`.
- `expectSearchInputFocused(page)`: consulta `document.activeElement.id` durante la ventana de 10 s que usa el resto de la suite.
- `addProductToCartViaKeyboard(page, sku)`: compone la secuencia búsqueda → foco de fila → Enter → Enter en "Agregar al carrito", reutilizada en los casos de manipulación del carrito.

### Ejecución local

```
pnpm run test:e2e:web -- --grep "keyboard-only /sales smoke"
```

La especificación completa tarda aproximadamente 5 min localmente (los 3 análisis de axe en línea del caso exitoso agregan unos 10 s; el resto corresponde a la limpieza de la base estándar de Playwright y los datos de prueba por caso). La suite E2E web es intencionalmente solo local para controlar los minutos de Actions; ejecútala antes de las versiones y cuando un cambio modifique estos flujos.

## Panel de pago adaptable

`SalePaymentModal` conserva su nombre público y contrato de formulario, pero renderiza mediante el `Drawer` compartido. El panel tiene un solo `role="dialog"` etiquetado, confina el foco, se cierra con `Escape`, bloquea el desplazamiento del cuerpo y restaura explícitamente el foco en `#sales-product-search-input`. El título de pago, el resumen del total, el formulario desplazable y el pie de acciones son cuatro regiones estructurales, para que un usuario con lector de pantalla o teclado no pierda la acción Confirmar al cambiar de modalidad de pago.

`e2e/web/payment-drawer-responsive.spec.ts` fija la geometría estable y la ida y vuelta del foco en 1440x900, 768x1024, 640x800 y 390x844. El caso de 640 píxeles CSS representa el diseño mostrado por una pantalla de 1280 píxeles con zoom del navegador al 200%; no reemplaza la validación del zoom nativo del navegador y del sistema operativo. La suite comprueba que las transiciones entre efectivo/tarjeta y pago dividido conserven el rectángulo del panel, mantengan accesibles los controles de cierre, total y confirmación, usen desplazamiento vertical interno sin desbordamiento horizontal y no emitan errores de cliente. Define `PUNTOVIVO_AUDIT_DIR` al ejecutar la especificación para capturar imágenes locales EN/ES sin agregar artefactos binarios a git.

### Política aplicada de correcciones en el mismo cambio

Cuando una comprobación enfocada de accesibilidad encuentre una regresión concreta, corrige el código compartido y agrega una aserción de regresión en el mismo cambio. Conserva las mediciones históricas de contraste en evidencia de revisión fechada, en lugar de tratarlas como validación actual. Los atajos deben seguir funcionando desde el campo de búsqueda de ventas y respetar la edición en los demás campos; las acciones no disponibles del carrito no deben mostrar controles deshabilitados ilegibles.

## Navegación móvil del espacio de trabajo

Por debajo del breakpoint de escritorio `xl`, la aplicación renderiza un panel de navegación dedicado en lugar de mantener la barra lateral de escritorio traducida en el árbol de accesibilidad. El panel abierto es un diálogo modal etiquetado y hereda el contrato compartido de diálogos: el foco entra en el control de cierre, `Tab` permanece dentro, `Escape` lo cierra, se bloquea el desplazamiento del cuerpo y el foco vuelve al control de apertura del encabezado.

El selector de espacio de trabajo es un grupo de opciones de selección única con navegación móvil por flechas, Home y End. Solo se montan las rutas del espacio seleccionado, para que los lectores de pantalla no recorran inventarios de rutas ocultos. Los cajeros omiten el selector porque su rol corresponde únicamente al espacio Vender. Los cheurones desplegables de escritorio anuncian la acción y el espacio por separado, por ejemplo `Expand Catalog` / `Collapse Catalog`, en lugar de duplicar el nombre del enlace adyacente al espacio.

La cobertura permanente de Playwright está en `e2e/web/navigation-responsive.spec.ts`, con 768×1024 y 390×844. Fija la selección del administrador, restauración de ruta directa, restricciones del cajero, cierre con Escape, restauración del foco al control de apertura, ausencia de desbordamiento horizontal y cero errores de cliente.

## Revisión de tecnología de asistencia

El hook compartido de diálogos aísla cada elemento hermano del fondo con `aria-hidden="true"` e `inert` mientras un modal está abierto. El aislamiento recorre cada nivel de ancestros, por lo que cubre tanto paneles basados en portales como diálogos de navegación en línea. El estado usa conteo de referencias y conserva los atributos anteriores; así la aplicación permanece oculta mientras hay diálogos apilados y solo se restaura cuando se cierra el último propietario. El foco entra en el diálogo activo antes del aislamiento y vuelve al control de apertura (o a un destino explícito de restauración) al cerrar.

El panel de pago expone un modal conciso a la tecnología de asistencia:

- el total es un estado atómico de anuncio no interruptivo, nombrado por su etiqueta visible localizada;
- las opciones del método de pago forman un grupo etiquetado y el select de respaldo de la biblioteca de formularios se elimina del árbol de accesibilidad;
- los fallos de validación y cobro son alertas, mientras que el desajuste del pago dividido es un estado de anuncio no interruptivo; y
- el orden de acciones móviles coincide con el DOM y el orden del foco (`Cancel`, luego `Confirm Sale`).

`e2e/web/assistive-technology.spec.ts` es la prueba semántica básica permanente. Con un viewport de 390×844 valida el diálogo del espacio de administrador en español y el panel de pago del cajero en inglés, incluidas etiquetas, regiones dinámicas, aislamiento del fondo, selección por flechas, Escape/restauración del foco, orden de acciones y cero errores del navegador. En 1280×800 también emula movimiento reducido y colores forzados: el cobro debe abrirse sin ninguna transición compartida en ejecución, mantener el foco dentro del diálogo, exponer límites de controles con colores del sistema y un anillo de foco visible, y evitar desbordamiento horizontal. Si defines `PUNTOVIVO_AUDIT_DIR`, la especificación guarda capturas de pantalla e instantáneas ARIA de Playwright como evidencia local de revisión.

## Seguimientos fuera del alcance

- **Revisión con NVDA en Windows** en los flujos de cajero y administrador. La automatización del navegador fija semántica y colores forzados simulados, pero la validación de versiones de Windows todavía necesita la revisión con el lector de pantalla nativo. La cobertura automatizada anterior no valida una estación de trabajo física ni una combinación nativa de tecnología de asistencia.
- **Consumidores de tablas restantes**: deben conectar las acciones principales mediante `onRowActivate` con restricciones de rol correspondientes. El `DataTable` compartido ya implementa la primitiva de navegación con teclado; valida cada consumidor cuando cambie su comportamiento.
